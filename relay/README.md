# Lantern encrypted relay

Worker module + D1 migrations for the private Sites relay. Source contains no deployment credentials. The live deployment is managed through the separate Sites checkout; copy changes from this directory and apply the migration manifest there before publishing.

The mobile PWA is public. Route traffic requires independent random host/client bearer keys. New PCs automatically enroll with a random 256-bit installation capability, saved in their encrypted workspace before the first request. Only its SHA-256 hash is stored by the relay. Send it to `POST /v1/installations` as a bearer; route creation uses `X-Lantern-Installation` plus the route host bearer. Never include the installation capability in a phone QR. This is anonymous, quota-limited enrollment, not a verified user identity. PC approval and the end-to-end handshake still control all access to chats.

Limits: 2,000 installations, 500 new installations/day globally, 100/day per edge-reported IP (a day-scoped salted digest, no raw IP stored), 12 active routes and 60 new-route attempts/day per installation, and 4,096 active routes globally. Retries with the same installation key and existing route renewals remain possible at quota. Unused installations expire after 90 days only when they have no active routes. These bounds limit abuse; anonymous enrollment cannot eliminate distributed denial of service. Capacity changes should be explicit operational changes.

Existing private PCs retain the short-lived HMAC proof verified by runtime secret `LANTERN_REGISTRATION_KEY`. Never put that secret in source or a client bundle. Existing routes may renew with their host key for backward compatibility. Native clients carry end-to-end mutual TLS; the PWA uses authenticated P-256 ECDH and AES-GCM records. The Worker never terminates either inner encrypted channel.

Each exchange authenticates and updates the queue in one atomic D1 batch. Every packet read and mutation checks the route key, active session and expiry. Clients can request `batch: 4` to drain up to four ordered packets or `pushOnly: true` to send independently of the receive loop; old clients retain the one-packet response. Queues remain bounded to 32 packets per direction. Acknowledgements commit even when a new packet hits backpressure, and conflicting retries are rejected.

Run `npm test` with Node 22.13 or newer. The tests use real SQLite behind a minimal D1 adapter. Production hosting needs a Sites project configured with D1 binding `DB` and both migrations plus their journal under `drizzle/`. Do not modify applied migrations or put service tokens into this repository or public app builds.

Build public web assets into the Worker with `npm ci --prefix pwa` then `node relay/scripts/build-web.mjs` from the repository root. The build fingerprints static assets to invalidate the service worker cache on every source change. Deploy the guarded registration endpoint and configure its runtime secret before switching an existing private Site to public access.
